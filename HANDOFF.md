The signature image (`public/images/signature.png`) is a **placeholder** the owner sent just to see the layout - it needs to be replaced with a real clean scan before this goes live (see section 6). **Printing fix (29 Oct 2026):** the first version of the print CSS used `visibility: hidden` to hide the rest of the site while printing, which left several blank trailing pages (hidden content still took up vertical space even though invisible). Fixed by giving the header, footer, floating WhatsApp/phone buttons and the portal's own name/tab bar an explicit `print:hidden` class (Tailwind's print variant, `display: none`) instead, so their height collapses too - the printed receipt is now exactly one page. The date/title/URL/page-number text some browsers print by default on every page is a **browser print setting**, not something this website can turn off: in the print dialog, turn off "Headers and footers" (sometimes under "More settings"). **"Download PDF" button (29 Oct 2026):** since that browser setting cannot be forced off from the website, and staff will generate many bills a day, the "Bill ready" screen has a **Download PDF** button that builds the PDF directly in the browser and downloads it with one click - no print dialog, no settings, ever, always A4 size since every bill is handed over as a printed A4 page. Built with `jspdf` and `html2canvas-pro` (both added as real npm dependencies - **not** `html2canvas` itself, which cannot parse the modern `oklab()` colour syntax Tailwind CSS v4 generates for any `/NN` opacity class anywhere on the page, e.g. `bg-paper/90`, and hangs forever instead of failing - this cost real debugging time, so if a future upgrade ever swaps it back to plain `html2canvas`, expect the same silent hang). The image is captured as a high-quality JPEG, not PNG (a plain PNG of a mostly-white receipt came out near 10 MB; JPEG at 92% quality looks identical and is under 200 KB). Both libraries are loaded only when a staff member actually clicks the button (a dynamic `import()` inside `src/utils/downloadInvoicePdf.js`), not on every page load - watch for this if adding future imports near there, since a plain top-level `import` would add ~600 KB to the bundle every visitor downloads, including people who never touch the admin panel. **No Print button (30 Oct 2026):** removed at the owner's request, since bills always go out as a downloaded/printed A4 PDF - Download PDF is the only option now.

**PDF genuinely fills the A4 page (30 Oct 2026):** the owner's first few downloads only used the top ~65% of the page, with a dead gap, because of a real bug: `PrintableInvoice`'s root div carries the A4 sizing classes (`max-w-[210mm]`, `min-h-[...mm]`), but both call sites wrapped it in a second, unstyled `<div ref={...}>` and pointed `downloadInvoicePdf` at *that* wrapper - which has no width of its own, so it stretches to whatever space its parent gives it (around 1156px on this page), not 210mm. `PrintableInvoice` now takes `ref` directly as a prop (React 19 - no `forwardRef` needed) and puts it on its own root div, so the capture always targets the real, correctly-sized box. A second, related bug hit only the "re-download a past bill" path: that render happens off-screen (`position: fixed; left: -9999px`) with no explicit `width` on that wrapper, so it shrank to fit its content instead of giving the receipt room to reach 210mm, making that specific capture narrower (and so, once stretched to fill a PDF page width, wrongly taller/shorter) than the normal on-screen one - fixed by giving that hidden wrapper an explicit `width: 1000px`.

**Single page unless the bill is genuinely too long (30 Oct 2026):** once the capture-target bugs above were fixed, a realistic bill (one service, a discount, a partial payment, plus a note) was still spilling onto a second page. The owner was clear about what's wanted: one page whenever the content fits, and only split, full-width, when it's genuinely too big - not a page shrunk sideways to force everything onto one sheet (that was tried and rejected: it leaves odd blank margins down both sides and no longer looks like a real A4 bill). The actual cause was that the receipt's own spacing was too generous to scale - the earlier "make it look like a full page" pass used a big logo, large type and wide gaps between sections (`p-12`, `mt-16`, `text-3xl` title, etc.) that measured out to 342.76mm tall for that bill, well past A4's 297mm, once the real extra lines (discount, amount paid, balance due, note) were included rather than just the bare minimum one service line. Fixed by scaling the whole receipt's spacing and type size down (`p-9`, `mt-8`/`mt-6`, `text-2xl` title, smaller logo and signature, tighter table rows), bringing that same bill down to 264.99mm - comfortably inside one page, with `min-h-[265mm]` on the receipt as the floor so a short bill still reads as a full page rather than a few cramped lines. `downloadInvoicePdf.js` was reverted to plain, full-width pagination with no shrinking and no overflow-tolerance fudge: it always renders at full page width and only adds a second (also full-width) page when the content is truly taller than one page. Verified directly (not just by reading the code): a simple one-service bill renders as 1 page; the exact discount+partial-payment+note bill from the owner's screenshot now renders as 1 full page at the new spacing; an 18-service bill correctly spans 2 full-width pages with no shrinking on either.

**Unstyled PDF right after a deploy (29 Oct 2026):** the owner's first bill after pushing the one-page fix (CKD-0009) came out as plain unstyled text with a huge logo. Cause: html2canvas draws from a *copy* of the page, and that copy re-downloads the site's stylesheet by URL. A tab opened before a Vercel deploy still points at the old hashed CSS file (`/assets/index-XXXX.css`), which no longer exists after the deploy, so the copy got no styles (the visible page still looked fine because it had loaded them earlier). Fixed in `downloadInvoicePdf.js` (`onclone: inlineLoadedStyles`): the copy now gets the styles this tab already has in memory, inlined as `<style>`, instead of re-downloading them; Google Fonts (cross-origin, unreadable) is left as a link, and the copy waits for `fonts.ready`. Verified on a real production build (`vite build` + `vite preview`, not just the dev server, which inlines CSS and so never showed this bug) by forcing the CSS file to 404 after page load: both a new bill and a re-download from "All invoices" come out styled and on one page. If the lazily-loaded PDF code itself is missing after a deploy, the error now tells staff to refresh with Ctrl + F5.

**Portal speed (29 Oct 2026):** the owner asked for a faster portal, but only if it stays completely error-free. The portal was already doing the big wins (login and check-in/out reply with everything the first screen needs, most tabs reuse that `boot` data, each request reads each sheet once). What's left is Google Apps Script's own ~1-2 s per request, which only a move off Google Sheets would remove. Deliberately NOT done, for correctness: showing cached/old data while refreshing, and "optimistic" screens that show a check-in or bill before Google confirms it. ## 10. Gotchas learned the hard way

- `package.json` has `"type": "module"`, so Node scripts that use `require` must be `.cjs` (the mock and runner are).
- On Windows PowerShell 5.1: no `&&`; use here-strings carefully; write Python/JS helper scripts to files rather than inline.
- Do not use the Write tool with short or odd paths (it once created stray files in `C:\`); always use full paths inside the project.
- `public/images/ckd-lead-banner.jpg` is 6.7 MB and is not referenced anywhere in the code; it is left out of the zips. Delete it from `public/images` if confirmed unused, or compress it.
- Google Apps Script idles; the first request after a pause can take a few seconds. `warmUp()` in `api.js` sends a harmless GET when the admin page opens.
- Do not name an exported helper file `.jsx` if it has no JSX (a `format.jsx` to `format.js` rename caused a stale Vite module graph; restart the dev server after renames).
